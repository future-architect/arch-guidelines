# 合意形成のための資料作成

技術判断は、その一段上にある相手の価値判断に従属させて組み立てる。「◯◯が決まれば、今回決めたいことが決まる」の◯◯を探し、その◯◯を決めるための論点を作り、筋の通ったストーリーにして資料にする。比較表の中身を順に説明する資料を作るのではない。

この会で推奨案に決めきるつもりで資料を作る。ただし、推奨が外れても、どこで外れたかが分かれば仮説の精度は上がり、目的は果たせる。外れどころは、背景の捉え方、要件、足切りの考え方、最後に残した案を選び分ける考え方、推奨案に追加で考慮したい条件のどれかである。資料は、相手がどこで違うと感じたかを指させるよう、背景→相談事項→要件→構成案と推奨の順に積み上げる。落選した案のフォロー（落選した案を選んだ場合の詳しい手当てなど）は優先度が低い。量が多くなるなら資料に入れず、外れたときに次回お持ちすればよい（書き方は `templates/material.md` の「弱みと緩和策」）。

本 Skill は手続き1〜7 を順に踏む。手続きは前のアウトプットを入力にするので、飛ばさない。題材によっては手続き2〜6 が数分で済むほど薄くなるが、それでも順に通す。

最初に `references/procedures.md`（サブステップごとの特記事項）を通読する。借りられる既成の型（絞り込みパターン、QCD、セキュリティの分類、5形式、トレードオフの型、当社の理解の分類）は `references/frameworks.md`、一周した例は `references/examples.md` にある。

ファイルで渡されたら、形式に合う Skill（pdf、pptx、docx、xlsx）で読む。読んだら、プロジェクト固有の背景知識（ミッション、ユースケース、体制、期限、重視していそうなこと）を先に抜き出しておく。

### 中期経営計画や提案資料が無いとき

相手と業種・規模が近い企業の公開資料を探し、その方針をそのまま相手の方針として使う。

1. 相手の業種と規模（売上、従業員数、上場区分など）を課題文や資料から読み取る。読み取れなければ、ユーザーに業種と規模だけを聞く
2. WebSearch で、同業かつ同規模の企業の中期経営計画、統合報告書、DX 推進の方針（DX 認定の公表資料など）を探す。1〜3 社に絞る
3. そこから、IT やデータに関わる重点（コスト削減、内製化、AI 活用、ガバナンス強化、グローバル展開、M&A による拡大など）の方向を抜き出す。他社の数値目標は相手の想定に使わない
4. 抜き出した方針を、相手の価値判断の当たりとして手続き2-1 以降で使う。検索できない環境なら、業界の一般的な方針を仮置きし、中間成果物の「仮に決めた前提」に書く

借りた方針は、中間成果物の「前提とインプット」に出典 URL と企業名を書き、手続き2-1 の当たりと 6-1 の判定にだけ使う。資料には書かない。相手の方針はそれまでのやり取りで共有済みとみなし、資料で説明し直さない。ただし、借りた方針が外れると推奨が入れ替わるときは、他社名を出さずに資料に出す。すでに決まっていて事実として答えが返るもの（海外拠点の有無など）は、推奨を左右する未確認の前提として1ページ目の確認事項に1行で書く。相手がこれから決めること（何を優先するか、計画を立てるか）は相手の価値判断が要るので確認にせず、手続き6 の問いに含める（方針そのものは問わず、その方針のために何を負うかを問う。`procedures.md` の 6-4）。

## 手続き1〜7 を踏む

各手続きの、やること・アウトプット・陥りやすい誤りを示す。誤りの列は、アウトプットを書いた直後のセルフチェックに使う。

### 手続き1 決めなければならないことを洗い出す

アウトプットは、決めたいことの一覧と決める順序。

| #   | やること                                                                     | 陥りやすい誤り                                                 |
| :-- | :--------------------------------------------------------------------------- | :------------------------------------------------------------- |
| 1-1 | 検討課題を分解してタスク化する                                               |                                                                |
| 1-2 | 確認事項（事実として答えが返る）と相談事項（相手の価値判断が要る）を区別する | 本来相談すべきことを確認として問い、相手に答えを求めすぎる     |
| 1-3 | 相手側のキーマンを確かめる。論点ごとに答える人が違えば対応付ける             | だれ向けの資料かを決めないまま作る。担当外の相手に判断を求める |
| 1-4 | 影響の大きさ、依存関係、リードタイム、ロールバックの可否から優先度を付ける   | 話しやすい議題から始め、前提になる議題が未決だと後で気づく     |

渡された課題が1つでも、その中に複数の決めごとが含まれていることが多い。今回の資料で扱う範囲と、後回しにするものを分けておく。

### 手続き2 落としどころを考える

アウトプットは、落としどころの仮説（推し案と、それを推す理由）。

| #   | やること                                                                                 | 陥りやすい誤り                                                 |
| :-- | :--------------------------------------------------------------------------------------- | :------------------------------------------------------------- |
| 2-1 | 背景資料から、相手の判断軸（コスト、スピード、セキュリティ、内製化など）に当たりをつける | 一般論での当たりとなり、説得力に欠く                           |
| 2-2 | 粗案を3〜4つ並べる                                                                       |                                                                |
| 2-3 | 自分の言葉で、落としどころの仮説を作る                                                   | ユースケースや要件が決まらないことを理由に、仮説を作らずに待つ |
| 2-4 | 推し案が浮かぶ理由を言葉にする                                                           | 推し案の理由が「なんとなく」のまま比較に入る                   |

推し案は外れてよい。仮説を持って外せば、どの判断軸の当たりがずれていたかが分かる。この時点で推し案を決めるのは、後の調査や比較に際限なく時間を使わないためでもある。

### 手続き3 取りうる案を考える

アウトプットは、案の一覧。

| #   | やること                                           | 陥りやすい誤り                                                   |
| :-- | :------------------------------------------------- | :--------------------------------------------------------------- |
| 3-1 | 案を出す。この段階では多いほどよい                 | 一覧に無い案を「この案は検討した？」と聞かれ、検討不足と見られる |
| 3-2 | 亜種を代表パターンにまとめ、亜種は代表の下に添える | 亜種を並べたまま比較表に載せ、列が増えて違いが見えなくなる       |

案出しの技法と、案が実質1つのときの扱いは `procedures.md`（手続き3）にある。

### 手続き4 各案を観点ごとに評価する

アウトプットは、比較表（案を列、観点を行。技術観点のまま中間成果物に書く）と、推奨案とその理由の一言。

| #   | やること                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | 陥りやすい誤り                                         |
| :-- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------- |
| 4-1 | 検討の対象に入らない案（決定済みの事項を覆す案（現行案を除く）、別の検討で扱う案）を除き、代表パターンで数えて案が4つ以上なら、要件（足切りに使えない条件は `references/procedures.md` の「絞り込んだ理由の残し方」）に照らして ❌（事実上対応できない）の付く案を足切りし、比較表に載せる案を減らす。3つ以下のとき、または ❌ の付く案が無いときは、足切りせず、すべて比較表に載せる。足切りで3つに満たなくなったら、足切りで外した現行案を比較の基準として比較表に加える。落とした理由と、候補に挙げた基準を残す | 全候補を精緻に比べようとして破綻する                   |
| 4-2 | 観点を挙げ、技術的に評価する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |                                                        |
| 4-3 | 前提を確かめ、プロジェクトの文脈（ミッション、ユースケース、体制）を代入して再評価する。足りない前提は仮に決め、表に明示する                                                                                                                                                                                                                                                                                                                                                                                       | 一般論の✅⚠️❌のまま進む                               |
| 4-4 | 観点を、差が出る・制約・差なしに仕分ける。文脈で制約になった観点（仮に決めた制約と、現行案だけが満たさない要求を除く。`references/procedures.md` の「絞り込んだ理由の残し方」）で ❌ が付く案は、代表パターンで数えて案が4つ以上なら足切りで外す（外した結果3つに満たなくなったら、4-1 と同じく現行案を加える）。3つ以下なら、比較表に ❌ のまま残す。下位互換の案も外さず比較表に残す。下位互換の案、❌ のまま残した案、比較の基準の現行案は、問いの選択肢には入れない                                            | 差の出ない観点を仕分けずに並べ、どこが論点かが埋もれる |
| 4-5 | 推奨案について自分たちの仮説を検証する。どの行を重く見たかを一言で書く                                                                                                                                                                                                                                                                                                                                                                                                                                             | 推奨が無く、相手任せに見える                           |

推奨案は✅の数では決まらない。一択になったら、優先度の選択の問いは作れない。推奨案に相手が負う弱み（費用や期間の増加、受け入れる制約）が残るなら弱みの許容として相談し、残らないなら結果を報告として扱う。足切りに使える条件は `references/frameworks.md` の絞り込みパターンに従う（負担と下位互換は足切りに使わない）。

### 手続き5 相手が判断できる評価軸に組み替える

ここから相手の目線に切り替える。アウトプットは、相手の言葉に直した評価軸。

| #   | やること                                                                                                       | 陥りやすい誤り                                                                 |
| :-- | :------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| 5-1 | 評価観点を、相手の関心事に紐づける                                                                             | 技術的な評価観点のまま提示し、相手が判断できない                               |
| 5-2 | QCD などの網羅性のある軸を大分類に借り、技術観点を中分類→大分類へ抽象化する                                    | なぜこの軸かと問われて答えられない                                             |
| 5-3 | 各評価軸を、プロジェクト文脈を加味して自然な言葉にする                                                         | 数百ミリ秒、RPO 15分をそのまま出し、相手が自分たちの使われ方に置き換えられない |
| 5-4 | だれに説明するかに合わせて翻訳の水準を変える。ビジネス部門なら大分類まで、要件定義の担当なら業務要件の水準まで | 技術が分かる相手と翻訳しないまま合意し、業務側の条件が後から出て手戻る         |

評価軸は、何を気にして何を決めればよいか、決め方によってどんな不都合があるかが読み取れる形にする。言い直しても相手の関心事にならない観点は、評価から外してよい。

### 手続き6 評価軸からコンセプト別の選択肢を作る

アウトプットは、コンセプト別の選択肢（品質優先A案、コスト最適化B案のように、何を優先する案かが名前で分かるもの）と、問いと報告の仕分け。

| #   | やること                                                                                                                                                                                                                                                   | 陥りやすい誤り                                                                                                               |
| :-- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------- |
| 6-1 | 相手の答えで推奨案が入れ替わり、かつ相手の価値判断が要る軸だけを論点に残す。判定は一般論ではなく相手の前提を代入して行う。差が出る軸のうち、それ以外は報告にする。差なしの軸は比較表の行に残すだけで、問いにも報告にもしない                               | 翻訳できない技術の差を論点に残し、相手の価値判断が要る差を落とす。報告で済むことに合意を求める。合意が要る事項を黙って進める |
| 6-2 | 決め手になる行だけ、文脈を注入して評価の精度を上げる。値は推奨案に合わせて恣意的に動かさない                                                                                                                                                               |                                                                                                                              |
| 6-3 | 案に、何を優先した案かが分かるコンセプト名を付け、デメリットを差の大きさの数値つきで整理する。相手が到底飲めないデメリットは、選択肢に出す前に前提として確かめる。推奨案が費用を増やすなら、`procedures.md` の「費用の示し方」に従って費用の比と効果を出す | 優先の構造を出さずに案を並べ、「どれがよいですか」と聞く                                                                     |
| 6-4 | 推奨案を添えて、どちらのコンセプトを取るかを問う。コスト差が小さければ推奨案のデメリットを許容できるかを、コスト差が大きい割に得る効果が小さければ、劣る側を別の施策で緩和する形でよいかを問う                                                             | 「どうですか」とだけ問い、自分たちが何を良いと考えているかを言わない                                                         |

問いは「これを取ると、代わりにこれを失うが、よいか」の形にする。同じ向きに働く論点は1つの問いにまとめる。比較表の行がいくら多くても、問いは数個に収まるのが普通である。

報告に含めるかの基準は `procedures.md` の「問いにするか、報告にするか」にある。

### 手続き7 説明用のストーリーと伝え方を組み立てる

アウトプットは、ストーリーと伝え方の計画。ストーリーは資料のページ割りとして書く。ページごとに、そのページで言い切るメッセージ1文、求めるアクション（報告・確認・基準への同意・優先度の選択・弱みの許容のどれか。資料にはこのラベルを出さない）、使う中間成果物を決める。お願いの文を書かないページ（経営層向けの並びの1ページ目、担当者向けの並びの相談事項）は、求めるアクションを「なし（お願いは推奨と比較の結び）」と書く。そのページに未確認の前提の確認があるときは「確認」、背景は「報告」と書く。

| #   | やること                                                                                                                                | 陥りやすい誤り                                                                                                   |
| :-- | :-------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| 7-1 | 推奨案と論点、背景、案の集合、トレードオフ、受け入れる弱みを、下の並びでストーリーにする。各要素で押さえることは `procedures.md`（7-1） | 落とした案の理由や比較の説明が、提案より先に続く。表をどう作ったかから説明し、相手が「今何の時間？」と迷子になる |
| 7-2 | 相手の反応を予想し、疑問が出そうな箇所に補足を入れる。相手の上司など別の利害関係者がだれでどう気にしそうかも添える                      | 想定していない質問で止まり、持ち帰りになる                                                                       |
| 7-3 | 相手の負荷と時間の制約から、伝え方を計画する。何回に分けるか、各回で論点を出し切るか決め切るか、どのページまで出すかを決める            | 一度に話す情報量が多すぎて相手がついて行けなくなる                                                               |

並びは、相談か報告か、相談ならさらに相手の立場で決まる。相談の並びは手続き1-3 で決めた相手の立場から選び、中間成果物の手続き7 の「並び」に理由を1行書く。資料を一緒に読み進めて中身を詰める相手なら担当者向け、冒頭の1ページだけで結論を掴みたい相手なら経営層向けにする。報告は、冒頭で結論を言い切り、背景はその後に置く。

- 相談（担当者同士のすり合わせ。既定）: 背景（相手側のビジネス上の背景だけ）→ 相談事項（相手目線で何を決めるか。いつまでに決まるとよいかは最後に。自分たちの都合で期限を述べるときは「システム構築を担う当社としては」と立場を限定し、「〜に決まることが好ましいと考えています」と書く。相手から見ると自分たちは利害関係者の1つで、プロジェクト全体の総意のように書くのは不遜になる）→ 要件（箇条書きで端的に）→ 構成案と推奨（提案と理由を言い切り、案の型と構成図、足切り（構成図の下端の ○× と文）、統合した比較表、問いの選択肢を選び分けるフロー図、結びに所感の問いかけを1か所）→ 問いの前提にならない報告 → Appendix（先頭に推奨案のデメリットと緩和策の節。ほかは比較表以外の補足だけ）。中身と、各要素を置く条件は `templates/material.md`
- 相談（経営層など、冒頭の1ページで結論だけを掴みたい相手）: 冒頭のサマリ（提案の言い切り、ご相談の対象、判断の決め手）→ 背景 → 当社の理解（今回の判断に関わる要件。2件以下なら背景に書き、ページは設けない）→ 推奨と比較（1ページにまとめる。足切り（構成図の下端の ○× と文）、フロー図を置き、結びに所感の問いかけを資料で1か所だけ書く。弱みと緩和策の図を入れた推奨案の節は Appendix の先頭に置く。中身と、各要素を置く条件は `templates/material.md`）→ 問いの前提にならない報告 → Appendix。問いの前提になる報告は、結論だけを冒頭のサマリに置き、根拠は推奨と比較のページに書く
- 報告: 決めた内容を言い切る（「◯◯としました」）→ 背景（なぜ今この報告か）→ 役割と採用理由 → 相手側の作業や運用への影響

## 成果物

作業ディレクトリ（ユーザーの指定が無ければカレントディレクトリ）に2つ書く。

1. `<題材>_中間成果物.md`: 手続き1〜7 のアウトプットを手続きの順に並べたもの。技術観点のままの比較表、足切りの表（資料には載せない）、評価軸の組み替え、論点の仕分け、ストーリーのページ割り、伝え方の計画もここに入れる。レビュアーがどの手続きで判断がずれたかを辿るためのもので、相手には出さない。`templates/intermediate.md` の型に従う
2. `<題材>_合意形成資料.md`: 相手に見せる資料。中間成果物の手続き7 のページ割りどおりに、ページを並べて書く。相手がそのまま受け取って読める完成品として、`templates/material.md` に従って書く

ユーザーがスライドや Word、Google ドキュメントなど別の形式を指定したら、資料の Markdown を正にして、その形式の Skill や Artifact で清書する。

## 書き上げた後の点検

`references/checklist.md` の点検を、資料と中間成果物の両方に当てる。引っかかったら、症状に対応する手続きまで戻って直す。後ろの手続きだけを直しても、手前が甘いままなら資料は良くならない。

自分で点検した後、別のレビュアーに資料を読ませる。観点の違う2つのレビューに分け、混ぜない。混ぜると、文面の細かい指摘に紛れて流れの穴が埋もれる。

| レビュー | レビュアーの役                         | 見ること                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | 返してもらう形                                                                   |
| :------- | :------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------- |
| 文面     | 日本企業のビジネス文書の校閲者         | 敬語と待遇表現の一貫性（貴社・当社、ご提案します）、ビジネス文書としての語調、不自然な日本語やねじれ、冗長と重複、残った技術用語、表記ゆれ（方式名、数字、単位）、表の見出しとラベルの自然さ                                                                                                                                                                                                                                                                                                              | 引用、問題、直し案、重要度。15件まで                                             |
| 流れ     | 相手（役職と技術の分かり具合を伝える） | 読み終えた直後に3行で要約させる（何を提案され、何の判断を求められ、決め手は何か）。要約が意図とずれたら構成の穴とみなす。読み進める途中で疑問や引っかかりが生じた箇所を、出た順に挙げさせ、後のページで解消したかも書かせる。その場で判断できるか、できないなら何が足りないか。あわせて、今決める理由（担当者向けの並びでは相談事項の最後、経営層向けの並びでは背景）と、後から変えた場合の記述を突き合わせ、推奨案の節で、推奨案のデメリットが、比較表で推奨案が劣る行をすべて拾っているかを確かめさせる | 要約、疑問の一覧（どのページのどの文か、解消したか）、判断に足りないもの、重要度 |

- 渡すのは資料だけにする。題材の設定や中間成果物は渡さない。相手が見るのは資料だけなので、資料の外の情報で補って読まれると穴が見えなくなる。図は、何が描いてあるかを文章で添える
- レビュアーは、Agent ツールで model に opus を指定した別のエージェントを使う。2つのレビューは並行して走らせてよい
- 流れの指摘は症状として扱い、checklist.md の表で戻る手続きを決めてから直す。文面の指摘は資料の文だけを直す。直したら、中間成果物の該当する手続きとページ割りも合わせて直す。すべての指摘に従う必要はない。題材の前提やユーザーの指示と合わないものは、理由を添えて見送る
- ページの構成や並びを直したときだけ、流れのレビューをもう1回かける。再レビューは1回までにする
- ユーザーが資料を手直ししたら、checklist.md の問いの形とコンセプト名の項目で、同じ内容を書いている箇所と中間成果物の手続き6・7 をそろえる
