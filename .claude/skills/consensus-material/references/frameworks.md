# 借りられる既成の型

## 案の絞り込みパターン（手続き4-1）

足切り（❌）に使えるのは、制約と、要件を事実上満たせない場合だけ。移植性・保守性の負担と下位互換は、比較表での評価に使う。

| 分類                 | パターン                   | 説明                                                                                                                                                                         | 資料での伝え方の例                                                                              |
| :------------------- | :------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| 制約                 | 技術制約                   | 相手の既存環境に載らないもの、既存システムとつながらないもの。自分たちの技術方針（サポート終了が近い製品は採らない、など）で落とすときは、相手と確かめて要件に入れてから使う | 「今の閉域網でつながるのは AWS だけなので、ほかのクラウドは除外します」                         |
| 制約                 | ビジネス制約               | IT 方針、法規制、契約に反するもの                                                                                                                                            | 「業界のガイドラインでデータを国内に置く必要があるため、国内リージョンのない製品は除外します」  |
| 要件の未達           | 機能要件                   | 今回の用途に要る機能（データ基盤なら、アクセス権限の管理やデータカタログ）を持たないもの                                                                                     | 「今回の用途で、これを満たさないものは検討から除外します」                                      |
| 要件の未達           | 非機能要件（性能・拡張性） | 今のデータ量や利用者数で基準を満たさないもの、増えたときに持ちこたえないもの                                                                                                 | 「3年後の想定データ量で基準を満たせないため、除外します」                                       |
| 負担（比較表で評価） | 非機能要件（移植性）       | 用途が固まらない段階で、特定の技術にロックインされ、後から載せ替えにくいもの                                                                                                 | 「用途が固まっていない現段階では、後から載せ替えにくい点が負担になります（載せ替えは約◯か月）」 |
| 負担（比較表で評価） | 非機能要件（保守性）       | 標準的な運用プロセスに乗らないもの、作り込みが要るもの、扱える人を確保しにくいもの                                                                                           | 「作り込みが要るため、運用の引き継ぎに約◯か月かかります」                                       |
| 劣位                 | 下位互換                   | どの観点でも、ほかの候補と同等か劣るもの                                                                                                                                     | 「◯◯は、どの点でも△△を上回らないため、選択肢には入れません」                                    |

## 評価軸に借りる既成の軸（手続き5-2）

システム構築では、大分類に QCD を借りると収まりがよい。Q の中身は ISO/IEC 25010 の品質特性（機能適合性、性能効率性、互換性、使用性、信頼性、セキュリティ、保守性、移植性）を参考にできる。ボトムアップの評価軸だけに頼ると「なぜこの軸なのか、観点に抜けは無いのか」と問われる。一般に受け入れられている分類を起点にすると納得感があり、自分たちも観点の抜けを防げる。

攻め・守りを大分類にするときは、性能や開発の速さを攻め、セキュリティや可用性を守りに振り分ける。相手がそのモードで判断しようとしているときに使う。軸は相手に何を問うかに依存する。大分類が QCD なら「品質、コスト、納期のどれを重視するか」という粗い問いになり、関心事まで下りると問いも細かくなる。

### セキュリティの分類

セキュリティは Q に入るが、単体では範囲が広すぎる。NIST や ISO の分類のまま並べてもビジネス側には伝わりにくいので、外部脅威か内部脅威か、事前の対策か事後の対策か、で分ける。

|                            | 外部脅威（サイバー攻撃、不正侵入）                       | 内部脅威（誤操作、内部不正、コンプライアンス）                    |
| :------------------------- | :------------------------------------------------------- | :---------------------------------------------------------------- |
| 事前: 発生を防ぐ           | (1) 外部防壁: WAF、DDoS 対策、脆弱性管理、攻撃面の最小化 | (2) 統制とアクセス制御: SSO、多要素認証、最小権限                 |
| 事後: 被害を抑え、証明する | (3) 被害範囲の局限化: テナント分離、異常検知、自動復旧   | (4) 監査と透明性: 操作ログの追跡、SOC2・ISO27001 などの第三者認証 |

アカウントや DB を分けるような分離度の高い構成は、外部の防壁よりも内部脅威と被害範囲の側で効く。分離を推奨するなら、4つのどこで効くかを示す。相手がそこを気にせず、専門家としても推奨しないなら、分離のコストに見合わないと判断できる。

## 相手へのコミュニケーションの5形式（手続き6、7-1）

観点はまず制約と評価に分かれる。制約は交渉の余地が無いので論点にせず、案を外すのに使う（案が3つ以下なら、比較表に ❌ で残す）。評価は重みが交渉可能なので、案同士で差が出れば論点にできる。論点に残った行は、何に合意するかで、基準への同意、優先度の選択、弱みの許容に分かれる。手続き6 のコンセプト別の選択肢は、このうち優先度の選択の形で問うものである。

| 区分                 | 形式         | 相手に求めること                                                                     | 使う条件                                                                                                                                         | 資料に要る記載                                                                                                                 |
| :------------------- | :----------- | :----------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| 相手の価値判断が不要 | 報告         | 決めた内容を把握してもらう                                                           | 相手の価値判断は要らない。自分たちで決めた                                                                                                       | 決めた内容と、その役割・採用理由                                                                                               |
| 相手の価値判断が不要 | 確認         | 想定が合っているかの確認                                                             | 推奨を左右するのに、まだ確かめていない前提がある。推奨を左右しない事実の確認は資料に載せず、中間成果物の伝え方の計画（事前に確かめること）に書く | 自分たちの想定と、推奨が切り替わる値                                                                                           |
| 相手の価値判断が要る | 基準への同意 | 案を落とす条件や振り分ける条件に同意を得る。結果は条件から決まり、相手は何も諦めない | 基準が相手側の方針や制約に依る。または候補が多く、今回は絞り込みだけを諮る。個別の判断をルールで束ねて合意する場合も含む                         | 基準と、それを適用した結果                                                                                                     |
| 相手の価値判断が要る | 優先度の選択 | 残った案のトレードオフのうち、何を優先し何を諦めるかを、推奨案を添えて合意する       | トレードオフ構造が出ていて、案ごとにどの重み付けなら選ぶかが言える                                                                               | 選び分けのフロー図（案ごとに負うもの）と推奨案の節（メリット、デメリットと緩和策の対）。スコープなら全体像と外したものの行き先 |
| 相手の価値判断が要る | 弱みの許容   | 推奨案に残る弱みを、緩和策込みで許容できるか確認する                                 | 推奨案が1つに絞れていて、弱みが許容できる範囲に収まっている                                                                                      | 推奨と比較の、推奨案の節（推奨案のデメリットと緩和策の対）                                                                     |

## 大分類で出やすいトレードオフ（手続き6-3）

| 分類             | メリット                         | デメリット                             | よく出る題材                   |

## 当社の理解の分類（手続き7）

経営層向けの並びの資料の「当社の理解」は、今回の判断に関わる要件を次の分類で並べる。分類の列を付けると、どの種類の要求が抜けているかを相手が見渡せる。担当者向けの並びでは列を作らず、要件の箇条書きが3項目以下なら並べる順に使い、4項目以上なら1階層目の項目にして2階層にする。

| 分類         | 入る要件の例                                                                           |
| :----------- | :------------------------------------------------------------------------------------- |
| 業務要件     | 止められない時間帯、対象の拠点や利用者、守る水準（再開までの時間など）                 |
| システム要件 | 使う基盤、連携する既存システム、データ量、セキュリティの要件                           |
| その他       | 稼働や設計の開始などの日程、予算の締め切り、体制、規程や契約、今回の範囲に含めないこと |
