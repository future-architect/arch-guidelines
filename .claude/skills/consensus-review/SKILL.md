# 合意形成編のレビュー

測れるものは測り、測れないものだけ目で見る。逆をやると、番号の崩れを目で追って見落とし、本文とケースの矛盾を lint に聞いて何も出ない。

| 見る人               | 対象                                                              |
| :------------------- | :---------------------------------------------------------------- |
| textlint             | 日本語の表現、決めた用語（`prh.yml`）                             |
| `check_structure.py` | 手続き番号、節あたりの太字、ローマ数字                            |
| 人                   | 本文とケースの整合、例の一貫性、翻訳の残り、`[要検討]` の鮮度、図 |

執筆ルールは `documents/forSoftSkill/consensus/CLAUDE.md` が持つ。先に読む。

## 1. 機械で回す

リポジトリのルートで流す。

```sh
npx textlint --config documents/forSoftSkill/consensus/.textlintrc.js documents/forSoftSkill/consensus/*.md
python3 documents/forSoftSkill/consensus/scripts/check_structure.py
```

どちらも0件になるまで直す。`check_structure.py` が末尾に出す、参照されていないサブステップと `[要検討]` の一覧は棚卸しの材料なので、件数の増減だけを見る。

`.textlintrc.js` で切ってあるルールは、本書の書き方と衝突するため。復活させると大量に出る。弱い表現の検出は残してあるので、問いの引用でない推量の文末は引っかかる。

## 2. 目で見る

機械で拾えないものを、この順で見る。

1. 本文の追加が、既存のケースと矛盾していないか。本文を足したら、その手続きを参照しているケースを必ず開く。本文に「劣後させた観点にも飲めない水準があるか確かめる」を足したのに、ケースが「劣後する観点を捨てる決断を促す」で終わっていると、逆を向く
2. 例が題材の中で一貫しているか。リージョン選定の例が途中から RPO やフェイルオーバーの話に流れる、のようなずれを見る。1つの題材は1つの軸で通す
3. 技術の単位が翻訳されずに残っていないか。「数百ミリ秒」「RPO 15分」は相手の言葉ではない。使う頻度と場面まで書けているか
4. `[要検討]` が現状と合っているか。中身が動いたら、開いている問いを書き直す
5. 太字が節の主張になっているか。数は機械が見るが、その1つが節でいちばん言いたいことかは読まないと分からない
6. 図と本文が同じことを言っているか。流れ図（`figures/gen_step_flow.py`）の手続きの名前・番号と、本文の見出しや（N-k）の項目が揃っているかを見る

## 3. 所見にする前に確かめること

- 参照番号を直すときは、本文の `## 手続きN` の見出しと `figures/gen_step_flow.py` の `STEPS` を正とする。本文中の参照を先に直すと、どちらが正しいか分からなくなる
- 用語を1つ禁止するなら `prh.yml` に入れる。本文だけ直しても次に書いたときに戻る
- 覆った案は書き残さない。確定したものを肯定形で書く
- 削る提案をする前に、`CLAUDE.md` の「密度のレビューで削らないもの」と、図・表の前の一言を残すルールに当たらないかを見る

## 4. 報告の形

- 機械の結果は件数だけ書く。全件を貼らない
- 目で見た所見は、どの手続きの記述と、どのケースが食い違っているかを対で書く
- 直したものと、判断を仰ぐものを分ける。方法論に関わる変更は判断を仰ぐ側に置く
