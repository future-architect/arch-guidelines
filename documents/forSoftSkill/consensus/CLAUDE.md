# 合意形成編

ソフトスキルガイドラインの続編。技術設計の課題を相手と合意するまでの手続きを扱う。リポジトリ全体の規約（導線の登録、区切りのスラッシュ、textlint の扱い）はルートの `CLAUDE.md` に従い、ここには本書に固有のことだけを書く。

## ページ構成

| ファイル                                                      | 扱うこと                                                   |
| :------------------------------------------------------------ | :--------------------------------------------------------- |
| `consensus_building.md`                                       | 本編。合意形成の構造、心構え、手続き1〜9                   |
| `failure_patterns.md`                                         | 相手の反応から、戻るべき手続きを引く逆引き                 |
| `case_studies.md`                                             | ケーススタディの一覧                                       |
| `case_multitenant.md` / `case_migration.md` / `case_genai.md` | ケーススタディ1〜3                                         |
| `veteran.md`                                                  | ベテランの進め方。ケースではこうだが実際はこう動く、を示す |
| `review.md`                                                   | レビュアーがメンバーをどう指導するか                       |
| `appendix.md`                                                 | 手続きをまたぐ体系や長い表、特定の題材への応用             |

ページを足したら、`.vitepress/config.mjs` の `links` の `/documents/forSoftSkill/consensus/` に登録する。

## 本編の手続きの書き方

手続き1〜9 の各章は次の型で書く。本文を短く保ち、9つの手続きを1つのモデルとして掴めるようにするため。

1. 見出しの直後、図の前に導入を一言二言。その手続きがなぜ要るかと、一般的な進め方と違う注意点を書く
2. 流れ図（`images/procedure{N}_flow.svg`）
3. 通し例（`> **在庫連携の例**: …`）。その手続きのアウトプットだけを1〜2文で書き、手続き1〜9 を主流のライン1本でつなぐ。理由・経緯・本筋から外れる枝はケーススタディに任せる
4. 「その他の特記事項を示す。」に続けて、サブステップ1つを箇条書きの1項目にする（`- （2-3）…`）。2-3 などで節を切らない。節を切ると長文に戻る
5. 1つのサブステップの判断を直接助ける派生の話は、`::: info （N-k）見出し` で囲み、どのサブステップの話かを番号で紐づける。同じサブステップの info は1つにまとめる
6. 図の箱や躓きと重なることは本文に書かない

本文に足したいことの行き先は次で決める。

- 本文や info に残す: 1つのサブステップの判断を助け、本文だけで読める長さのもの（言い回しの ❌✅ 例、短い型の表）
- `appendix.md` へ: 手続きをまたぐ体系や長い表、特定の題材への応用、`[要検討]` が中心の未確定の型
- `failure_patterns.md` へ: 相手の反応や症状から入る話
- `review.md` へ: メンバーに意図を確認する、促すなど、レビュアーの振る舞い
- `veteran.md` へ: 進め方の流儀
- 削除: 図、特記事項、既存の info と重複するもの

本文から Appendix へ移したら、本文側の参照を「（→Appendixの、見出し名）」に直す。

## 執筆ルール

### 書式

- 太字は1節（`###` / `####` の1ブロック、または `##` 直下の導入文）に1つまで。節の主張を1つ選んで付ける。`[要検討]` マーカーには使わない
- 箇条書きの項目ラベル（`- **状況**:` のような行頭の見出し語）は太字でよく、上の予算に数えない
- 見出しと表のヘッダー行は太字にしない。見た目はテーマ側で決める
- 箇条書きの項目の末尾には「。」を付けない（項目の途中の文の区切りには付ける）
- 箇条書きが4項目以上になるときは、分類の項目を設けて2階層にする（ケーススタディの題材の設定は、決まった項目の並びなので除く）
- 章や層の番号はローマ数字ではなく (1) (2) (3)。段階は 1-1、2-3 のように書く

### 強調と言い換え

- 強調のための「」は使わない。「」は発言、資料の文言、問いの引用にだけ使う
- 言い換えのカッコ補足（道筋（ストーリー）など）は書かない。一番伝えたい語を1つ選ぶ。カッコは具体例、数値、定義のように情報が増えるときだけ
- 章や節の名前は、中身の項目を並べず、それらを抽象化した語にする（業務の要求と制約を並べる節は「要求事項と制約」ではなく「要件」）
<!-- textlint-disable prh -->

- 議論で出た比喩や造語（取るもの・捨てるもの、など）を本文の用語にしない。メリット・デメリットのように読み手が一般に知っている語で書く

<!-- textlint-enable prh -->

### 構成

- 本文は1次元のストリームとして読ませる。前の手続きへの参照はよいが、後の手続きへの前方参照（→手続き6-1 で確かめる、など）は書かない。後で効くことを伝えたいときは、参照先の番号ではなく、それを抽象化した目的（比較の観点を挙げるときの出発点になる、など）で書く。冒頭の全体像は対象外
- 本文はケーススタディに依存させない。本文は一般論として単体で成立させ、ケース側から段階番号を参照する。ただし `veteran.md` は、ケースではこうだが実際はこう動く、を示すためにケースを参照してよい
- 図と表の前には、何の図・表かを示す一言を必ず置く。レビューで予告文と指摘されても削らず、直すなら書き換えにとどめる
- 補足のページの図や本文では、本編で説明した語（比較表など）や、名前で分かることを再説明しない。そのページ固有の主張だけを書く

### 断定の強さ

- 根拠が1〜2件の見解は断定しない。「〜という進め方をとる人もいる」の形にするか、`[要検討]` にする
- 「もっとも」「最大の」「頻出する」などの程度の断定は、根拠を示せない限り書かない
- 議論で覆った案は書き残さない。「Aではなく B」の対比にせず、確定した B を肯定形で書く

### 用語

<!-- textlint-disable prh -->

- 相手任せの表現（相手に決めてもらう、相手に委ねる、決断を下してほしい、相手しか決められない）は使わない。プロとして推奨案を示し、相手の価値判断が要る点は選択肢とトレードオフを提示して合意する、という姿勢で書く（相手の価値判断が要る、相手と合意する、推奨案を添えて確認する）
- 人や立場の呼び方は次のとおり
  - 合意を取りに行く先は「相手」。相手側の個人を指すときだけ「相手側の担当者」のように書く。「顧客」「クライアント」は使わない
  - 指導を受ける側は「メンバー」、指導する側は「レビュアー」（「レビューア」「指導層」は使わない）
  - 提案する側は「自分たち」（「我々」は使わない。「こちらを重視すれば」のような指示語は可）。役割を指すときは「提案者」（「コンサルタント」は使わない）
  - ケーススタディで自分たちの会社は「開発会社」（「ベンダー」は使わない）
  - 経験を積んだ人は「ベテラン」（「経験者」「熟練者」は使わない）
- 「相手」を「意思決定者」に置き換えない。相手が意思決定者か持ち帰り型の担当者かを見極めること自体が手続きの一部のため。説明している最中の、聞く側の反応を描く箇所に限り「聞き手」も使ってよい
- ガイドライン自身は「本書」と書く
- 「誰」はひらがなで「だれ」、「躓く」「躓き」は漢字で書く

## ケーススタディの書き方

- 題材の設定は、相手・自分たち・現行・計画・きっかけ・決めたいこと・方針の箇条書きで書く
- 題材は技術のドメイン知識を前提にしてよい（読者はアーキテクト）。そのほうが、技術の観点を相手の言葉に直す手続き5・6が引き立つ。上流の要件から従属的に決まる題材（RPO/RTO が決まれば決まるバックアップ頻度など）は、合意すべき論点が上流にあるので選ばない
- 資料で自分たちの希望（期限など）を述べるときは、「システム構築を担う当社としては」のように立場を限定し、プロジェクト全体の総意のように書かない。相手から見ると自分たちは利害関係者の1つにすぎない。この限定の句と「〜が決まることが好ましい」は相手任せの表現にあたらず、密度のレビューでも削らない
- 相手の業務で出る効果の数値（窓口の工数を月約500時間減らせる、など）は推奨理由の1か所だけに書き、繰り返さない。自分たちで根拠を答えにくい数値が独り歩きするため。費用の比のように自分たちで説明できる数値は再掲してよい

## 失敗パターンの選び方

`failure_patterns.md` は、相手の発言から戻る手続きを引くためのページで、発言から原因が1つに絞れる失敗だけを載せる。

- 載せないもの
  - 健全な反応（「推奨案でよいです」）と、理解が進んだ相手の健全な問い（「なぜこの構成になるのですか」）
  - 原因が多様で絞れない反応（「持ち帰って読みます」）、新しい情報が無い反応、発生頻度が低い反応
- 書き方
  - 反応はセリフだけを書く（「〜」と聞かれる、などを付けない）
  - 並びは相手の理解の段階順（目的の理解 → 案の理解 → 選択の理解）
  - 節の本文に原因を書き、次に「処方箋となる手続き: 」を書く

## 密度のレビューで削らないもの

文を削るときは、削っても読者の行動が変わらないかで選ぶ。次は副次効果や警告に見えても残す。

- 指示の理由になっている文。理由がない指示には従いにくい
- 読者のためらいを解く文（相手にとっても、事前に見ておけば考える時間が取れる、など）
- 行動の理由になる警告と、相手からの信頼を損なうという警告。信頼関係の構築と合意形成が本書の本旨のため

## 図

- 図の生成元は `figures/gen_*.py`。`python3 figures/gen_<名前>.py` で `images/` に SVG を書き出す。図を直すときは SVG を手で直さず、スクリプトを直して再生成する
- `images/procedure_flow.svg` と `images/value_structure.svg` は手書きの SVG で、それ自体が生成元
- ケーススタディの PNG（`images/case_*.png`）は生成元がない。文言を直すときは、図をスクリプトで作り直して `figures/` に置く
- 図のキャプションは SVG の中に描かず、図の直下に斜体の段落（`_キャプション_`）として置く。使い道は区分の論拠や出典で、文末に「。」は付けない。出典を示せない区分は、出典があるように書かず、分け方の説明にとどめる
- 見た目の確認は cairosvg で PNG にして見る（`python3 -c "import cairosvg,sys; cairosvg.svg2png(url=sys.argv[1], write_to=sys.argv[2], scale=2)" in.svg out.png`）

## 検査

リポジトリのルートで流す。どちらも0件になるまで直す。

```sh
npx textlint --config documents/forSoftSkill/consensus/.textlintrc.js documents/forSoftSkill/consensus/*.md
python3 documents/forSoftSkill/consensus/scripts/check_structure.py
```

- `.textlintrc.js` は、ルートの設定に本書の書き方（箇条書きの末尾に「。」を付けない、問いを「ですます」で引用する、など）と、`prh.yml` の用語の辞書を重ねたもの
- `check_structure.py` は、手続き番号の実在、節あたりの太字の数、ローマ数字を見る。サブステップの正は `figures/gen_step_flow.py` の `STEPS`。末尾に出る `[要検討]` と参照されていないサブステップの一覧は、指摘ではなく棚卸しの材料
- 機械で拾えない整合（本文とケースの矛盾など）は、`consensus-review` Skill の手順で見る

## 指摘をルールに足す

レビューで書き方の指摘を受けたら、直した後に一般化できるかを考え、できるものは次に足す。同じ指摘を繰り返させないため。ケース固有の事実（数値、題材の設定）は足さない。

- 本書全体に効く書き方は、このファイルの執筆ルール
- 機械で拾える語の言い換えは `prh.yml`。足す前に、本文や引用にその語が出てこないかを確かめる
- 用語を1つ禁止するときは、本文だけでなく `prh.yml` にも入れる。本文だけ直しても、次に書いたときに戻る
